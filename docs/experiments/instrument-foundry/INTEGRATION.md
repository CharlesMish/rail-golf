# Independent submissions and integration

Give each author the same pinned kit, contract, contributor brief and two
references. Invite one considered instrument per author. Do not preassign one
model a terrace, another an amphitheater and another a box puzzle: that would
manufacture variety rather than test independent invention. A short initial
concept note can prevent expensive engine work outside the contract.

## Submission boundary

Authors add data under a unique `worlds/instruments/<id>/` directory and a concise
evidence note. Local/session import makes registration unnecessary during design.
They preserve the fixed engine, recordings and historical files. Changing a
layout or revising an imported wrapper requires a new id. Use a stable suffix
such as `-v2` instead of overwriting an existing authored identity.

The starter packet contains documents, JSON and probes, not a separate engine
distribution. Its `SOURCE.json` names the exact public repository commit needed
for the existing validator and audition player. This avoids shipping a second
copy of the runtime that can silently diverge.

## Review in four separate decisions

1. **Data acceptance:** run strict instrument/probe validation before physics.
   Reject scripts/assets, extra fields, off-detent launch settings, unsupported
   geometry and conflicting ids. A valid file is eligible for audition, not
   automatically worth registering.
2. **Physical evidence:** replay the submitted families and ordinary neighbors.
   Inspect actual contact timing, pitches, gains, terminal outcomes and resource
   disposal. Compare multiple construction histories for touching surfaces.
   A self-reported `sourceBuild` alone proves nothing.
3. **Owner audition:** play without the numerical appendix first, in solo and
   against a retained phrase. Ask whether the environment suggests another
   meaningful shot. Keep sparse, accessible instruments in consideration.
4. **Integration:** retain only distinct, credible contributions. Preserve weak
   experiments as reports rather than filling the repertoire to a quota.

The existing references were selected through owner play, not because they
maximize a survey count. A new model need not beat their number of notes. A
single useful reply can contribute to an ensemble. Equally, a technically rich
world may remain too opaque to discover without a recipe.

## Registration after selection

The primary registry is `lib/instrument-catalog.js`. A reviewer can add a selected
JSON import to its `REGISTERED` list, after checking unique identity and
the same validation used for imports. This makes it available without reimporting
on every visit; it does not authorize changing ordinary Worldcraft presets or
the original Counterline repertoire. Keep the reference fixtures and their exact
physical/acoustic comparisons as regression controls.

The six additional slots are shared by registered instruments and session imports,
beside the two references. Reload clears only the session imports.

Before accepting a data-only PR, run its instrument validator, focused instrument
tests, TypeScript, lint and the repository test/build suite. A code extension is
a separate engineering review with old identity/replay comparisons. Optional
barrel geometry is currently such a separate study, not an approved v1 JSON kind.

Keep each selected instrument's provenance, measured baseline, negative results
and owner invitation beside its data. Publish an experimental collection preview
before any decision about production. No production integration is implied by
winning the authoring round.

## Remaining design questions

- Does a new instrument inspire a different live answer, or mostly another
  recording to listen to passively?
- Can a player discover more than one useful region without numerical recipes?
- Does moving origin provide understandable musical variety?
- Are repeated contacts expressive, or merely waiting through settling?
- Do the existing register and timbres genuinely prevent a desired role? If so,
  describe that role from listening evidence before enlarging the sound palette.
- Can a bounded curved element earn generic support without weakening historical
  snapshot validation or hiding a different collider under its visual surface?
